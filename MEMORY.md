

## Feature: remote Flux worker (Kaggle GPU) + hardening — IMPLEMENTED

**What:** `outside_text` inpainting can run Flux Klein 4B/9B on a user's remote GPU instead of locally. Popup `Inpainting quality` values `flux_klein_{4b,9b}_remote` are UI-only — `content-script buildTranslateRequest()` maps any `*_remote` to the real backend `inpainting_method` (`flux_klein_4b`/`_9b`) plus `flux_remote_base_url` / `flux_remote_token`. Docs: `docs/HUONG-DAN-CHAY.md` section 8.
- **Boundary:** `core/image/inpainting.py:FluxKleinInpainter.inpaint_mask()` — only the inference step goes remote (`_run_remote_inference`, `POST {base}/inpaint`); crop/blend/cache stay local. `backend/flux_worker.py` (run on the GPU box) reuses `_run_local_inference`. Protocol: `POST /inpaint {image_base64,width,height,seed,num_inference_steps,variant}` -> `{image_base64}`, `GET /health`.
- **Auth:** worker `--token` / `FLUX_WORKER_TOKEN`, header `X-Flux-Worker-Token`, `hmac.compare_digest`, on `/health` and `/inpaint`. 9B is HF-gated: worker `--hf-token`/`HF_TOKEN`.
- **Failure = graceful skip**, never a failed page: returns the original region. Module-level circuit breaker (2 failures -> skip that URL for 60s; connect timeout 5s; success resets). Reason surfaces as `warnings` (`flux_remote_unreachable` / `flux_remote_unauthorized`) on `TranslateResponse`/`TranslateBatchItemResponse`, collected per request via the `remote_warning_sink` ContextVar + `translate.py:_run_with_warnings` (ContextVar again because tests mock signatures). Content script shows a toast (`notifyBackendWarnings`, deduped 1/min per code) — content script has its OWN i18n tables, separate from `shared/i18n.ts`.
- **Gotchas:** inpaint disk cache leaks between tests (monkeypatch `should_use_inpaint_cache`); zero-size toggle inputs need `evaluate` + dispatch `change` in Playwright; toasts replace each other, so tests record them with a MutationObserver.
- **Not verified:** a real Kaggle GPU run (protocol verified locally worker<->backend only).

## Feature: story-aware professional translation (character DB, relationships, glossary) — IMPLEMENTED

**Status (2026-09-19):** implemented on branch `feature/professional-translation-context`, all tests green (backend `pytest` incl. new `tests/test_story_context.py`, `npm run build`/`lint`/Playwright incl. new `tests/story-context.spec.ts`). Requested by the repo owner, who pointed to their other project https://github.com/QuangTQV/novelforge-ai as inspiration, then explicitly scoped it as **an optional feature that requires login** — this changed the storage design from the original plan below (client-side only) to server-side per-account storage, since login implies persistence.

**Final design (supersedes the earlier "client-side, no Postgres" plan):**
- New backend module `backend/core/story_context.py` — one Postgres table `story_contexts` (JSON text columns for characters/relationships/glossary, one row per story, keyed by `account_email`), same plain-SQLAlchemy-Core shape as `core/server_config.py` but multi-row/per-account instead of a singleton.
- New `backend/auth.py:require_login` — unconditionally requires a valid account token, **independent of `MT_REQUIRE_AUTH`** (same shape as `require_admin`, minus the admin-email check). This means a user can log in via the Account tab and use the Story DB feature without the deployment operator ever turning on `MT_REQUIRE_AUTH`/quota enforcement — login and quota-gating are now decoupled.
- New router `backend/endpoints/stories.py` (`GET/POST /stories`, `GET/PUT/DELETE /stories/{id}`), all gated by `require_login`, mounted in `main.py`. `main.py`'s lifespan also calls `story_context.ensure_schema()` whenever `settings.database_url` is set (not gated on `require_auth`, unlike the accounts/server_config schema checks).
- `endpoints/translate.py:_resolve_story_context()` — when the request carries `story_id` and `account` is a real logged-in `Account`, fetches that story server-side and populates `req.story_characters/story_relationships/story_glossary` (new `TranslateOptions` fields, server-populated only) before `_build_config()`. Client never re-sends the character DB — just a `story_id` reference (extension's `AppSettings.activeStoryId`, sent only when `accountToken` is set).
- `core/config.py` gained `StoryCharacterConfig`/`StoryRelationshipConfig`/`StoryGlossaryTermConfig` dataclasses + 3 list fields on `TranslationConfig`, following the exact precedent of `FallbackProviderConfig` (nested dataclass list, not flattened scalars — flattening is only used for `fix_hint`'s fixed 3 fields).
- `core/services/translation.py:_format_story_context()` builds a `## STORY CONTEXT (character database)` prompt block, inserted right after `{context_memory_section}` and before `{ocr_input_section}`/`## TASK` in both the one-step and two-step prompts — close to STORY MEMORY in priority, while free-text `## STORY NOTES` (`special_instructions`) stays last/closest to `## TASK` so manual notes can still override the DB.
- Extension: new "Story DB" popup tab (`extension/src/popup/index.html`/`index.ts`), locked/editor toggle mirroring the Account tab's `#account-logged-out`/`#account-logged-in` pattern; dynamic Character/Relationship/Glossary/Continuity-Notes row editors modeled on `renderProviderGroups()`; `background/index.ts` has `storiesList/storyGet/storyCreate/storySave/storyDelete` mirroring `accountApiCall`.
- **Continuity notes, simplified per the user's explicit ask ("cho phép bật tắt là được" — just needs an on/off switch)**: NOT the full novelforge-ai "cross-episode facts ledger" (no auto-extraction, no categorization into completed/revealed/state_changed, no per-chapter linkage beyond a free-text `source_label`). Just a plain user-maintained list of `{text, source_label?}` per story (`StoryContinuityNote`/`StoryContinuityNoteConfig`), plus one `continuity_notes_enabled` boolean on the story row. `_resolve_story_context()` only populates `req.story_continuity_notes` when that story's toggle is on — unlike characters/relationships/glossary, which are always sent once non-empty. Rendered as a 4th, last subsection (`### Continuity Notes`) in `_format_story_context()`'s output. Off by default (a long-running series' notes could otherwise pile up token cost every request).

**Borrowed from novelforge-ai (context for *why* the design looks this way):** a Context Broker/Resolver split (prompt declares what it needs, a separate resolver step fetches/assembles it — here, `_resolve_story_context()` + `_format_story_context()`); "surface relation" between characters instead of deep psychology/trust-conflict-intimacy scores; a named-asset glossary (name+description per term) for consistent skill/item/nickname translation; the general idea of tracking what's been revealed across chapters (heavily simplified into continuity notes above). **Explicitly not adopted:** vector RAG/Qdrant/reranker, character psychology/dialogue-simulation tables, and novelforge's full categorized/auto-extracted facts ledger — overkill for short manga-bubble translation.

**Still deferred (not implemented, no open plan):** a "new name/term detected, not yet in glossary" auto-suggestion after each page, and upgrading `/suggest-instructions` to return structured JSON (characters/glossary) instead of free text for the popup to auto-fill. Neither was part of the core ask; revisit only if requested.

## Feature: "Live AI" debug logger (input/output of every LLM call) — IMPLEMENTED

**Status (2026-09-19):** implemented on the same branch, all tests green (301 backend pytest total, incl. new `backend/tests/test_live_ai_log.py`). Requested by the repo owner: log every AI call's input/output, gated by one env var so it's off unless deliberately enabled. Clarified via two questions before building: (1) log to a file **and** add a viewing API (not file-only), (2) text-only content — no raw image bytes, just a count + approximate KB (images are large, unreadable in a log, and not needed for debugging prompt/response text).

**Design:**
- `backend/config.py`: `live_ai_log_enabled: bool = False` (env `MT_LIVE_AI_LOG_ENABLED`) + `live_ai_log_path` (`backend/logs/live_ai.jsonl`, already covered by the repo's generic `logs/` gitignore entry — no new ignore rule needed). Independent of `require_auth`/hosted mode — useful for a self-hosted operator debugging their own setup, not just a centrally-hosted deployment.
- `backend/core/live_ai_log.py` (new): `log_ai_call()` (no-op unless enabled; appends one JSON line: provider, model, `call_type`, system_prompt, prompt_text, images_count/images_kb — never raw image data —, response_text, error, latency_ms; single-generation rotation to a `.1` backup past 20MB) and `read_recent_live_ai_log(limit)`.
- **Single hook point, not ~10 provider edits**: `core/services/translation.py:_call_llm_endpoint_impl` is the one function every provider dispatch funnels through (confirmed via Explore agent before touching anything) — used by `/translate`+`/translate/batch` (via `_call_llm_endpoint`'s retry loop), `/suggest-instructions` (`generate_character_notes` → same `_call_llm_endpoint`), and `/test-key` (`test_api_key`, which calls it directly, bypassing rotation). The **old** `_call_llm_endpoint_impl` body (the actual `if provider == "Google": ... elif ...` dispatch chain) was renamed to `_dispatch_llm_call`; the **new** `_call_llm_endpoint_impl` is a thin try/except wrapper around it that logs on both success and failure, then re-raises. This means zero changes to any of the ~10 per-provider branches.
- **`call_type` ("translate"/"suggest_instructions"/"test_key") is passed via a `contextvars.ContextVar`, not a function parameter** — found the hard way: `tests/test_rotation.py` patches `_call_llm_endpoint_impl` directly with ~15 fixed-arity mock functions (`(candidate, parts, prompt_text, debug, system_prompt)`, no `**kwargs`), so adding a parameter to that call site broke all of them. The ContextVar is set once at the top of `_call_llm_endpoint` (param `call_type: str = "translate"`, explicit `"suggest_instructions"` from `generate_character_notes`) and in `test_api_key` before its direct call — always freshly set immediately before use, so no reset/token bookkeeping needed despite `ThreadPoolExecutor` reusing worker threads across unrelated calls. (One unrelated, single-file mock — `test_suggest_instructions_web_search.py`'s `fake_call` — got a small `**_kwargs` addition instead, since that one patches the outer `_call_llm_endpoint`, not the inner impl, and only needed a one-line fix.)
- `backend/auth.py:require_live_ai_log_access` (new): a no-op when `require_auth` is off (self-hosted — the feature is already opt-in via the env var, no extra login needed to view your own local log), delegates to `require_admin` when `require_auth` is on (a hosted deployment's log can contain *other* users' prompts/translations, so only the configured admin may view it).
- `GET /admin/live-ai-log` (in `endpoints/admin.py`, `?limit=` query param, `LiveAiLogResponse`/`LiveAiLogEntry` in `schemas.py`): 404s when the feature itself is disabled (distinguishes "disabled" from "no calls yet"), otherwise returns recent entries newest-first.
- No extension/UI changes — the repo owner only asked for the backend log + a viewing API, not a popup panel.

**Verification:** unit tests for the logger module (no-op when disabled, JSON shape, image-exclusion, rotation, corrupt-line handling) + wiring tests that mock only `_dispatch_llm_call` and assert the real `_call_llm_endpoint`/`test_api_key` paths log the right `call_type` (including a same-thread call_type non-leakage check) + endpoint auth-gating tests. Then verified live: real `uvicorn main:app` process, `MT_LIVE_AI_LOG_ENABLED=true`, a real `POST /test-key` with a missing API key (fails fast, no network needed) actually appears via a real `GET /admin/live-ai-log` call with the correct `call_type: "test_key"` and error text — full real HTTP round trip, no mocks.


## Feature: Story DB relationship map + character assets — IMPLEMENTED

- **Relationship map** (`extension/src/popup/relationship-graph.ts`): an SVG *view* over the character/relationship form rows (rows stay the single source of truth; a MutationObserver + input/change delegation redraws). Drag nodes, click to highlight, "Connect" mode (click two characters -> pre-filled relationship row), click an edge label to jump to its row. Pointer capture only starts once a drag begins — capturing on pointerdown retargets the click to the `<svg>` and breaks selection.
- **Persistence without a migration:** node position `x`/`y`, `avatar` and `reference_images` are optional fields on `StoryCharacter` inside the existing `characters_json`; `ensure_schema()` validates columns so avoid adding columns for small optional data. Row state lives in `row.dataset` (`x`,`y`,`avatar`,`refs`) and `collectStoryCharacters()` reads it.
- **Assets:** popup downscales via `popup/image-utils.ts` (avatar 96px square, refs 448px, JPEG). Backend validates data URLs/size (`schemas.py`). Reference images are opt-in per request (`story_use_reference_images`, popup toggle in Story DB tab) and are appended after the page images with a labelled note (`translation.py:_format_story_reference_note`); they count against OpenAI-Compatible's media limit.
- **Bug found & fixed on the way:** the LLM translation cache key ignored the Story DB context entirely (editing a glossary kept serving the old cached translation when temperature was deterministic). It now hashes it.
- **Gotchas:** Playwright file choosers work with the detached `<input type=file>` the popup creates; the test PNG must be a *valid* PNG (`createImageBitmap` rejects a made-up one).
- **Not verified:** a real LLM actually using the reference images (only that they are sent and described in the prompt).


## Feature: Economy mode (API-cost saver) — IMPLEMENTED

Popup Translate-tab toggle (`TranslateConfig.economyMode`). Non-destructive by design: `extension/src/shared/economy.ts:effectiveConfig()` returns a *copy* with `imageDetail:'low'`, full-page and previous-page context off and Story DB reference images off, applied at request time only (content-script `buildTranslateRequest`, background request builder) — the user's stored values are never rewritten, so turning it off restores them. Context memory is left as-is (it's the cheap consistency option). Request field `economy_mode` also makes the backend (`pipeline/wrapper.py:_build_config`) shrink the full-page context image (768px vs 1536, media resolution medium vs high); bubble crops stay high-res. Playwright `tests/economy-mode.spec.ts` checks both the request and that stored settings are untouched.
