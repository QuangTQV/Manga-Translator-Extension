## Lessons learned (generalizable — worth remembering before touching related code)

- **Pydantic `Optional[X] = None` serializes as JSON `null`, key always present — never an omitted key.** A hand-written test fixture that just leaves the field out is NOT equivalent to what the real backend sends. Caused a real bug: `data?.x !== undefined` passed for `null`, then `String(null)` → `"null"` → `NaN` → a garbled relationship-map node. Fix: check `typeof data?.x === 'number'`. Write at least one test with the field explicitly `null` when a bug could depend on this.
- **A CSS flex item's `width: 100%` isn't cancelled by `flex:none` (or any `flex: 0 0 auto` variant).** Grow/shrink/basis go to `0 0 auto`, but when basis is `auto`, the main-axis size still comes from a separately-specified `width`. **Recurred twice** — the Story DB draft-discard button, then the Help chat's Send button — both reusing `.btn-add-fallback` (`width:100%`) in a flex row without also setting `width:auto`, both squeezing the sibling element down to its min-content width. **Any button that reuses `.btn-add-fallback` inside a flex row needs an explicit `width:auto` alongside whatever `flex:` override it gets — check for this every time, it's not obvious from reading the rule.**
- **MV3 service worker: never fire-and-forget (`void fn()`) a side effect that must survive past a message handler's response.** The worker can be torn down the instant the handler resolves; an un-awaited promise chain (e.g. `chrome.storage.local.set()`) can be cut off mid-flight. Always `await` it first, even for something that feels like "just bookkeeping."
- **`chrome.runtime.sendMessage()` cannot deliver a message back to the exact same script/context that sent it** ("Could not establish connection. Receiving end does not exist."). A test that needs to invoke a background message handler directly must send from a *different* extension context (e.g. a popup page opened via `context.newPage()`), not from `worker.evaluate()`.
- **Chrome MV3 action popups cannot be reliably drag-resized via CSS `resize:both`** — the browser continuously re-measures the popup's "natural" content size and can snap it back mid-drag. The reliable alternative: open the same page as a real `chrome.windows.create({type:'popup', url:'...'})` window, which the OS resizes normally.
- **Zero-size `.toggle input` checkboxes** (`opacity:0; width:0; height:0`) can't be hit by Playwright's `.check()`/`.click()` even with `force:true` — use `locator.evaluate(el => { el.checked = true; el.dispatchEvent(new Event('change', {bubbles:true})); })`.
- Rebuilding after a source edit matters: `npx playwright test <file>` runs against the *existing* `dist/` — use `npm test` (builds first) or you'll debug stale code.
- **A backend process started with plain `python main.py` never hot-reloads edited source files.** Verifying a backend fix by importing/calling the function directly in a one-off script proves the *code* works, but the actual running server (extension-facing) still serves the old behavior until it's restarted. Always restart it (or confirm the running PID's start time is after the edit's mtime) before declaring a live fix verified end-to-end.
- **A custom `html.parser.HTMLParser` subclass that tracks nested "skip this subtree" state via a push/pop stack must special-case HTML5 void elements** (`meta`, `link`, `img`, `br`, `hr`, `input`, ...). They get a `handle_starttag` call but no matching `handle_endtag` (no close tag exists), so pushing a stack entry for them desyncs every subsequent push/pop pair for the rest of the document — the very first stray `<meta>` silently corrupts the skip-tracking for everything after it. Symptom looked like "skip regions are leaking into content" but was actually "the stack no longer pops what it thinks it's popping." Fix: no-op in both `handle_starttag` and `handle_endtag` for void tags.
- **Padding a search query with bias keywords (e.g. "wiki characters") to steer a general engine toward reference sites can silently break exact/fuzzy title-matching backends** (Bing, and especially a dedicated title-database API like MangaDex's) for anything but the most common titles — verified live, appending those words took a query from an exact single-result match to zero results. If a query needs to work well on both "broad relevance ranking" and "exact title lookup" engines in one shared request, keep it to the bare identifying string and push disambiguation to a later step (e.g. domain-priority re-ranking of results, or letting a model request its own follow-up) instead of padding the query text itself.
- **`content-script/index.ts`'s `.mt-page-overlay` class declares `display: block !important` *and* `opacity: 1 !important`** (so a freshly created overlay is never accidentally invisible). Any later JS that wants to change either property on that element — not just `display`, which already had a comment about this — must use `el.style.setProperty(prop, value, 'important')`, not a plain `el.style.prop = value` assignment; the plain form is silently a no-op against the stylesheet's `!important`. Caught this the hard way adding opacity cross-fades: a from-scratch Playwright test with a hand-rolled minimal stylesheet (missing the real `!important` rule) passed convincingly, then the *actual* extension test (`view-original-toggle.spec.ts`) failed because it exercises the real cascade. When verifying a DOM/CSS fix by reconstructing the logic standalone rather than loading the real built extension, the reconstruction has to include every competing style declaration, not just the JS being tested — otherwise a "verified" fix can still be broken in production. Prefer running the real `.spec.ts` suite (or the actual loaded extension) over a hand-rolled repro whenever the real one is reasonably reachable.

## Standing UI-placement decision (governs all new advanced/pro-user features)

Advanced/pro-translator features must not be scattered onto the main Translate/LLM Config tabs — that clutters the UI for a casual reader. New work like this goes in its own space (the Pro tab, or a feature's own existing specialized tab like Story DB) that a casual user never has to see. **Already-shipped things directly on the main screen are NOT to be migrated** into that space unless explicitly asked again — the repo owner has twice deferred that restructuring ("để nguyên đi, tạm thời chưa cần").

## Features implemented (reference only — see the code/tests for exact behavior)

**Story DB** (character DB / relationships / glossary / continuity notes) — `backend/core/story_context.py`, `endpoints/stories.py`, popup "Story DB" tab. Requires login (`auth.py:require_login`, independent of `MT_REQUIRE_AUTH`); injected into the prompt server-side via `story_id`.
- Relationship map (SVG view over the form rows, drag/connect/click-to-highlight) + character avatar/reference images (`popup/relationship-graph.ts`, `popup/image-utils.ts`).
- Unsaved-draft recovery (`chrome.storage.local['mtStoryDraft:<id>']` — an MV3 popup is destroyed, not hidden, on blur) and Undo/Redo (Ctrl+Z/Shift+Z, debounced 600ms checkpoints) — share the same `input`/`change`/`MutationObserver` wiring.
- "Update from a description" (`POST /stories/update-from-description`, `verify_token`-gated, stateless) — free-text note → AI-drafted character/relationship/continuity-note updates for review before Save; optional web search (`enable_web_search`), deliberately not spoiler-safe (tracking plot developments is the point).
- Import/Export as JSON (`.mtstory.json`) directly in the tab.
- **Prompt placement (2026-09-25):** the whole Story DB (all characters, relationships, glossary, continuity notes) is sent every request, deliberately unfiltered — manga speakers are rarely named in their own bubbles, the default LLM-OCR one-step mode has no text before the call, and DB names are in the target language while page text is source-language, so any "only relevant characters" filter would silently drop exactly the speakers whose pronouns Story DB exists for. Cost is handled by caching instead: `_append_story_context_to_system` puts the block at the END of the translation system prompt (identical for every page of a run → Anthropic `cache_control` / OpenAI-Gemini-DeepSeek prefix caching), with only a one-line pointer + the per-request reference-image note left in the per-page prompt. Per-page STORY NOTES still sit next to the task and win on conflict (the system block says so). Don't reintroduce per-page filtering without accounting for it breaking that cache.
- **Per-site mismatch warning + explicit master toggle (2026-09-25):** `activeStoryId` is one global setting, not per-site. `TranslateConfig.useStoryDb` (off by default) gates whether Story DB is applied to translation at all; `background/index.ts:recordStoryDomainUsage()` remembers the last story actually used per hostname, and the popup warns (never auto-switches — explicit repo-owner choice) when the active tab's hostname doesn't match the currently selected story. Known gap: the warning doesn't fire when the popup is opened as the standalone window (below) — fails closed, not wrong.

**Manual editing tools** (content-script, backend `core/manual_region.py`):
- Manual region tool (drag a box → OCR → type/AI-translate → redraw) — `/region/ocr|translate|render`.
- Eraser tool (freehand brush cleanup, `cv2.inpaint` on a hand-drawn mask) — `/region/erase`, one cumulative mask per page.
- Move/delete a detected bubble's box — reuses manual-region `restore_only` to paste back real pre-translation pixels.
- Bold/Italic toolbar on the manual-region translation field (wraps selection in markdown markers).
- Shared limitation: `cv2.inpaint` doesn't reconstruct a fine repeating pattern (dense hatching/screentone) through an erased/cleaned area.
- Not yet verified on a real manga site (MangaDex-style `blob:`/lazy-loading pages) — only Playwright fixtures + synthetic images so far.

**Popup window** — resizable via CSS `resize:both` (unreliable, kept as a harmless bonus) plus a reliable "⤢ open in a separate window" button (`chrome.windows.create`, `?standalone=1`), remembers its own size separately from the anchored popup's.

**Popup UX polish batch (2026-09-24):** confirm-before-discard on the draft banner; a fixed, auto-hiding status banner; `background/index.ts`'s network-error strings now go through `t()` instead of hardcoded English (backend `HTTPException` text itself is still English — needs backend-side i18n, not attempted); tab grid fixed to an even 3-column layout for 6 tabs.

**"?" help chat (2026-09-25):** always-visible header button opens a full-overlay chat panel (over whatever tab is active), answering "how do I use this" questions with the user's own configured LLM. Explicit repo-owner choices: ground it in the project's own docs rather than a plain FAQ or bare LLM call, and persist history in `chrome.storage.local['mtSupportChatHistory']` across popup reopens (same reasoning as the Story DB draft-recovery work — a Chrome action popup is destroyed, not hidden, on blur).
- Backend: `POST /support-chat` (`endpoints/translate.py`), `verify_token`-gated (same one-off-LLM-helper family as `/suggest-instructions`/`/stories/update-from-description` — no login required for the normal self-hosted setup). `core/services/translation.py:generate_support_chat_reply()` flattens the whole conversation into one `prompt_text` (not a native multi-turn array — `_call_llm_endpoint`'s shared signature is single-shot, and every other call site through that choke point already works this way, so this follows the same shape rather than changing the shared function). Grounded in `README.md` + `docs/HUONG-DAN-CHAY.md` (not `docs/API.md` — that's backend-integration reference, not "how do I use this") — small enough combined to send in full every request rather than building real RAG/embeddings; `_load_support_chat_docs()` caches them in memory after the first read, resolved relative to the repo root (`Path(__file__).resolve().parents[3]` from `core/services/translation.py` — get this off-by-one wrong and it silently reads nothing rather than erroring, since a missing doc file is just skipped).
- Extension: reuses `popup/index.ts:firstEnabledProvider()` (same "just the first configured key, not full rotation" simplification as Update-from-description) and proxies through `background/index.ts` (`SUPPORT_CHAT` message, `fetchSupportChat()`) like every other cross-origin LLM call. `uiLanguage` is mapped to its full English name (`UI_LANGUAGES.find(...).name`) before sending — a raw 2-letter code like `"vi"` in a prompt is a needless ambiguity a full name avoids.
- **Not verified with a real LLM call** (no API key available in this environment) — same limitation as every other AI-helper feature built this session; covered by prompt-construction unit tests (real doc-file I/O, no mocking of the file read) and a mocked-network Playwright suite for the popup UI/persistence.
- Assistant replies render Markdown via `popup/markdown.ts` (paragraphs, headings, nested lists, fenced code, bold/italic/code/links) — builds DOM and assigns `textContent` only, never `innerHTML`, so a model reply can't inject markup; a test asserts an `<img onerror>` in a reply stays inert text. User messages stay plain text.

**Story DB free-text fields auto-grow (2026-09-25):** role, voice notes, relationship, relationship notes, glossary notes and continuity-note text are `<textarea class="textarea textarea-auto">` (`popup/index.ts:createAutoGrowField`) using CSS `field-sizing: content` — one line tall when short, growing with the text (capped at 180px, then scrolls). Native Chrome sizing, no JS resize; fine since the extension is Chrome/Edge-only. Short fields (name, glossary term/translation, continuity source label) stay single-line inputs.

- **The bug**: every provider adapter in `utils/endpoints/*.py` returns `None` or `""` instead of raising when a provider's safety layer blocks the content (e.g. Gemini's `promptFeedback.blockReason`, `utils/endpoints/google.py:~99`) or returns no candidates/empty content — confirmed identically shaped in `anthropic.py`, `azure_openai.py`, `deepseek.py`, `moonshot.py`, `openai.py`, `openrouter.py`, `openai_compatible.py`, `xai.py`, `zai.py`. `_call_llm_endpoint`'s candidate-rotation loop (`core/services/translation.py`, the single choke point every OCR/translate/suggest call goes through specifically *to* get key/provider rotation) only rotated to the next candidate on an exception or `_looks_like_a_refusal(result)` — and `_looks_like_a_refusal` explicitly returns `False` for `None`/`""` (by design, for a different reason: so it only ever matches an actual refusal sentence). Net effect: a safety-blocked primary candidate was treated as a "successful" result and returned immediately, **without ever trying the configured backup keys or fallback providers** — the exact feature those exist for. The falsy value then failed far downstream in `_parse_llm_response_unified` (which does correctly raise on `None`/`""`), by which point it was outside the rotation loop and became a flat HTTP 500 to the extension. An outer retry (pipeline.py's `except TranslationError` re-raise on "empty response"/"api failed" tokens) wouldn't have helped either, since `_iter_llm_candidates` always starts from the primary again — a deterministic safety block fails the exact same way every retry, never actually reaching a backup/fallback.
- **The fix**: in `_call_llm_endpoint`'s candidate loop, treat a falsy result the same as a refusal *for rotation purposes only* — `continue` to the next candidate when one exists. Deliberately did **not** change what happens on the last candidate (still returns the falsy value as-is, same as before) — every caller of `_call_llm_endpoint` already does its own `None`/""-handling right after the call (most immediately raise their own `TranslationError`), so changing that case too would've been a second, overlapping behavior change beyond the actual bug, and risked changing non-rotation call sites (`suggest_instructions`, the SearXNG ReAct follow-up round) that currently tolerate a graceful `None` in ways not fully audited.

Full rotation suite (37 tests) and a `-k translation or rotation or pipeline or ocr` sweep pass; the 56 unrelated failures in a full `pytest tests/` run are `MT_REQUIRE_AUTH=true` in this repo's own `.env` causing 401s on endpoint tests that don't send a token — confirmed pre-existing via `git stash` (same failures, same count, on a clean checkout).

## Done 2026-10-07 (real translation-quality bug: Vietnamese pronoun pairs flip-flopping across pages)

Owner-reported: the same two characters sometimes get sibling-register pronouns (anh/em) and sometimes peer-register (tớ/cậu) across different pages of the same story — inconsistent, not wrong in isolation but jarring across a chapter. This is a fourth entry in the same failure-mode family `tests/test_pronoun_prompt.py`'s docstring already tracks (misjudging relationship from art, PRONOUN MAP being decided fresh every page, over-defaulting to "tôi"/"bạn").

**Root cause**: the Vietnamese pronoun rule's `Evidence priority` ranked a page's own dialogue tone/register *above* anything already established for a pair — including the user's own Story DB `address_notes` and a prior page's decided `XƯNG HÔ:` pair — so a page that merely *read* more formal/casual than the last one could flip the pair even though nothing in the story actually changed.

**Fix, planned and refined twice with the owner before coding** (see the conversation that produced this — not just a straight "lock it" fix, two real edge cases were raised and had to shape the design):
1. First cut proposed locking an established pair unless the *current line* had a brand-new address term — owner pointed out this would entrench an early wrong guess forever if a later page provides the real answer.
2. Final design splits "established" into two tiers in `core/services/translation.py`'s `vietnamese_pronoun_rule`: **Story DB's `address_notes`** (user-authored, near-ground-truth) is hard to override — only a real in-story relationship-change beat can shift it, never tone alone. **A prior page's own guessed `XƯNG HÔ:`/`PRONOUN MAP:` pair** (only exists when Context Memory is on — no Story DB note covers this pair) is a *correctable default*, not a lock: a later page with clearer, more decisive address-term evidence can still fix an earlier wrong guess; what's banned is switching back and forth over a page merely sounding different.
3. `_format_story_context()`'s relationship line changed from `"... (by surname)"` to `"... — address as: by surname"` so the address note reads as an instruction the new rule can point to, not a passing parenthetical.
4. `extension/src/shared/i18n.ts`: `placeholderRelationNotes`/`hintStoryRelationships` (all 5 locales) now give a concrete example and say explicitly that this field, once filled in, is used consistently across every page — nudging users to actually populate the field the new rule leans on.

Deliberately out of scope: no schema/UI change (reused `address_notes` free text — a fixed dropdown of Vietnamese pronoun pairs would be both incomplete and premature), no `context_memory` storage/capping change (the existing 10-page/20-story LRU in `content-script/index.ts` was already adequate), no equivalent rule for non-Vietnamese output languages (a real idea raised in the same conversation, but separate). No live-LLM A/B verification possible in this environment (no API key) — same limitation as every other prompt-engineering fix in this file; verified via `tests/test_pronoun_prompt.py` (3 new tests, now a documented "Failure mode #5") and `tests/test_story_context_prompt.py` (updated for the new relationship-line format). Full backend suite: 56 failed/481 passed/79 skipped — same 56 pre-existing failures as the documented baseline, +3 passed matching the 3 new tests.

## Done 2026-10-07 (popup: animate the tab-switch height change, layer 2 of the "tab click feels jarring" complaint)

Owner reported the tab-click animation still felt "giật mạnh" (jarring), "not as good as macOS/iOS" — even after the 2026-10-02 fix that softened `popup-tab-enter`'s content fade/scale curve. That prior fix targeted the wrong layer: `.tab-pane { display: none/flex }` is a `display` swap (can't be CSS-transitioned), and `body` has no fixed height unless the user has manually drag-resized (`POPUP_SIZE_KEY = 'mtPopupSize'`) — so for the common case, the actual Chrome popup *window* auto-fits to the active tab's content height, and tabs vary a lot (Config/Account short, Translate/Story DB/LLM Config tall). Switching tabs snapped the whole window to a new height instantly; no inner-content easing can mask that.

Planned with the owner first (two rounds — approach confirmed via AskUserQuestion given real uncertainty about how Chrome's native auto-sizing would interact with an animated height, vs. the simpler fallback of just pinning one fixed size). Implementation in `popup/index.ts:activateTab()`: reuses this file's own `animateHintTo()` idiom (pin start height → swap → measure target → transition → clear back to auto on `transitionend`), skipped entirely for the standalone window, a saved/dragged custom size (new `userHasCustomPopupSize` flag, set in `restorePopupSize()` and both resize handlers — respects the user's choice rather than fighting it), or `prefers-reduced-motion`.

Two real bugs found and fixed via empirical Playwright probes (temporary, deleted after — this genuinely couldn't have been verified by reading code alone, exactly the live-testing risk flagged in the plan):
- **`document.body.scrollHeight` can never report less than the box's own current height.** Measuring the new pane's target height via `scrollHeight` while body was still pinned to the (possibly taller) old height always failed to shrink — it just reported the old height back. Fixed by momentarily releasing the pin (`height: ''`), reading the natural `getBoundingClientRect().height` once reflowed, then re-pinning to the start value before animating — all synchronous, so nothing is visibly shown at the natural size in between.
- **`transitionend` bubbles, and other elements (tab buttons' own color/border transitions) fire it too** — a `{ once: true }` listener on `body` got silently consumed by the first *unrelated* bubbled transitionend (e.g. a button's `color` transition finishing) before the real `height` one ever arrived, leaving the pin stuck forever (confirmed: `body.style.height` never cleared, `popup-height-animating` class never removed). Fixed by checking `e.target === document.body && e.propertyName === 'height'` before manually removing the listener, instead of relying on `once`. Note: `animateHintTo()` (the function this was modeled on) has the same latent `{once:true}`-vs-bubbling shape — hasn't visibly misfired there in practice (hints are leaf elements with nothing inside them to fire a competing transitionend), left alone since it's out of scope and not reported as broken.

Verified via direct Playwright probes sampling `getBoundingClientRect().height` every 20ms across a real tab switch (both grow and shrink directions settle smoothly via the `cubic-bezier(.16,1,.3,1)` curve, matching `popup-tab-enter`'s), a rapid-triple-click stress case (no stuck class/height, settles at the correct final tab), and both skip paths (`emulateMedia({reducedMotion:'reduce'})` jumps instantly with no inline height ever set; a pre-seeded `mtPopupSize` stays pinned, no animation class, tab switch never resizes the window).

## Done 2026-10-08 (real bug: Help chat numbered lists restarted at "1." on every blank line)
